# Hospital Patient Management & Eye Check-up System

A web application for a government hospital's ophthalmology department: patient registration, eye examinations, patient history, follow-up management, and summary reports with PDF/Excel/CSV export.

- **Backend:** Python 3.12, FastAPI, SQLAlchemy 2, Pydantic 2, Alembic, PostgreSQL (psycopg 3), ReportLab, openpyxl
- **Frontend:** React 19 + Vite, React Router, Tailwind CSS 4, Axios, React Hook Form, Recharts, Lucide icons
- **Tests:** pytest (112 API tests on an isolated database), Vitest + React Testing Library (25 tests), Playwright browser workflow test (22 checks)

## Quick start (local)

Requirements: Python 3.12+, Node.js 20+ (tested on 24), PostgreSQL 14+ (tested on 18).

### 1. Create the database role and databases

Run in `psql` as the `postgres` superuser (pick your own passwords):

```sql
CREATE ROLE hospital_app LOGIN PASSWORD 'choose-a-password';
CREATE DATABASE hospital_db      OWNER hospital_app;
CREATE DATABASE hospital_test_db OWNER hospital_app;   -- used only by the test suite
```

The app role does not need superuser rights. The first migration enables the `pg_trgm` extension, which PostgreSQL 13+ allows a database owner to create.

### 2. Backend

```powershell
cd backend
python -m venv .venv
.venv\Scripts\activate             # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
copy .env.example .env             # Linux/macOS: cp .env.example .env
```

Edit `backend/.env`: set `DATABASE_URL`, `TEST_DATABASE_URL`, and a random `SECRET_KEY`:

```powershell
python -c "import secrets; print(secrets.token_urlsafe(64))"
```

Create the schema and load demo data:

```powershell
alembic upgrade head
python -m app.seed                 # 4 demo users + 150 synthetic patients
python -m app.seed --patients 0    # demo users only
```

Start the API:

```powershell
uvicorn app.main:app --reload --port 8000
```

Interactive API docs: <http://localhost:8000/docs>

### 3. Frontend

In a second terminal:

```powershell
cd frontend
npm install
npm run dev
```

Open <http://localhost:5173>. The Vite dev server proxies `/api` to `http://127.0.0.1:8000`, so the refresh-token cookie stays same-origin.

## Quick start (Docker)

```bash
cp .env.example .env        # set POSTGRES_PASSWORD and SECRET_KEY
docker compose up -d --build
```

- App: <http://localhost:8080>
- API docs: <http://localhost:8080/docs>

The backend container runs `alembic upgrade head` on start. To create accounts:

```bash
# Production: create one admin interactively, then add staff from User Management
docker compose exec backend python -m app.seed --create-admin

# Demo only: set ENVIRONMENT=development and SEED_* passwords in .env first
docker compose exec backend python -m app.seed
```

PostgreSQL is not published to the host. Data lives in the `pgdata` volume.

## Deploy: Render (backend + database) and Vercel (frontend)

The browser only talks to Vercel. `frontend/vercel.json` rewrites `/api/*` to the Render backend, so the refresh-token cookie stays first-party and no CORS setup is needed for normal use.

**1. Render (backend + PostgreSQL)**

1. Render dashboard → **New → Blueprint** → choose this repository. `render.yaml` creates the `hms-db` database and the `hms-backend` web service.
2. When prompted, set:
   - `CORS_ORIGINS`: your Vercel URL, e.g. `https://hms.vercel.app`
   - `BOOTSTRAP_ADMIN_PASSWORD`: password for the first admin (username `admin`; 8+ chars with upper-case, lower-case and a digit)
3. After the deploy, open `https://<service>.onrender.com/api/health`. It should return `{"status":"ok","database":"ok"}`.
4. Sign in as `admin` and create staff accounts under User Management. Then delete `BOOTSTRAP_ADMIN_PASSWORD` from the service's environment.

Migrations run on every start (`alembic upgrade head`). `SECRET_KEY` is generated by Render.

**2. Vercel (frontend)**

1. If Render gave the service a URL other than `https://hms-backend.onrender.com`, update the `/api` rewrite destination in `frontend/vercel.json` and push.
2. Vercel → **Add New → Project** → import this repository → set **Root Directory** to `frontend`. The framework (Vite) and build settings come from `vercel.json`.
3. Deploy. Leave `VITE_API_BASE_URL` unset.

Free Render instances sleep after inactivity, so the first request after a pause can take about a minute. Render's free PostgreSQL databases expire after a limited period; use a paid plan and the backup steps in [docs/BACKUP_AND_RECOVERY.md](docs/BACKUP_AND_RECOVERY.md) for real patient data.

## Features

**Patient registration.** IDs like `PT2026000123` come from a PostgreSQL sequence, so they are unique and never reused. Age is calculated from date of birth. While the form is being filled, the app looks up existing patients with the same mobile number or a similar name and the same date of birth (trigram similarity). On save, possible duplicates return `409 possible_duplicate`; staff can confirm "different person" (for example, family members sharing a phone). An exact match on name plus date of birth or mobile cannot be overridden. Records store who created and last updated them.

**All patients.** Server-side pagination, search (ID, name, mobile), sorting on every column including last check-up and check-up count, and filters for gender, age range and registration date. Filters are kept in the URL.

**Unified search.** One box searches patient ID, name, mobile number and check-up ID, and shows matching patients with their recent examinations.

**Patient details.** Overview, check-up timeline, and medical history (diagnoses, prescriptions, doctor remarks, follow-up history). Every view is printable.

**Eye check-up.** Separate OD/OS sections. Visual acuity accepts Snellen, decimal, N-notation and CF/HM/PL/NPL. Sphere must be ±30 D and cylinder ±15 D, both in 0.25 D steps. Axis must be 0–180° and is required when a cylinder is recorded. IOP must be 0–80 mmHg. The same rules exist as PostgreSQL CHECK constraints. Saving shows a confirmation summary first. A client-generated `submission_id` makes the create request idempotent, so a double-click cannot create two records. Recommending a follow-up creates a pending follow-up. Edits are written to the audit log with old and new values. The system never generates diagnoses or prescriptions.

**Check-up report.** Printable on-screen report and a server-generated PDF with hospital letterhead, both eyes' measurements, assessment, follow-up, and a signature block with the doctor's designation and registration number.

**Follow-ups.** Views for upcoming, due today, overdue, completed, missed and cancelled, with counts. Search by patient and filter by date. "Overdue" is computed (pending and past due); the system never changes a status on its own. Completing a follow-up records who did it and when.

**Reports.** The dashboard shows KPI cards and charts: daily and monthly registrations, daily check-ups, age groups, gender, common diagnoses, and check-ups per doctor. There are eight reports: daily, weekly, monthly, registrations, examinations, doctor-wise, follow-up pending, and repeat patients. Filters cover start/end date, doctor, gender, patient ID and check-up type. Every report exports to PDF, Excel or CSV, or prints. All figures come from SQL aggregate queries. Exports are audit-logged, and spreadsheet cells are protected against formula injection.

**Administration.** User management (create, edit role/status, reset password). Audit log viewer with filters and a before/after diff. Settings page for profile and password changes.

## Database design

| Table | Purpose | Key constraints |
|---|---|---|
| `users` | Staff accounts | unique `username`, `email`; `role` CHECK; lockout fields |
| `refresh_tokens` | Issued refresh tokens (rotation/revocation) | unique `jti`; FK users ON DELETE CASCADE |
| `patients` | Demographics and reported history | unique `patient_code`; gender CHECK; DOB ≤ registration date; soft delete (`is_active`, `deleted_at`, `deleted_by`); `created_by`/`updated_by` FKs |
| `eye_checkups` | Examinations | unique `checkup_code`, `submission_id`; FK patient/doctor ON DELETE RESTRICT; range CHECKs on sphere/cylinder/axis/IOP; follow-up date required when follow-up is required, and on/after exam date |
| `followups` | Scheduled follow-ups | status CHECK; `completed_at` set only when status is completed; FKs RESTRICT |
| `audit_logs` | Append-only audit trail (JSONB old/new values) | UPDATE/DELETE blocked by trigger |

Indexes cover foreign keys, registration and examination dates, mobile number, `lower(full_name)`, a GIN trigram index on names, `(patient_id, examination_date)` and `(status, scheduled_date)`.

Clinical history is never cascaded away: deleting a patient is a soft delete, and the RESTRICT foreign keys make hard deletion of a patient with records impossible.

Schema changes go through Alembic:

```powershell
alembic revision --autogenerate -m "describe change"   # review the generated file
alembic upgrade head
alembic check                                          # verifies models and migrations match
```

## API overview

All endpoints are under `/api` and documented at `/docs`. Errors use one format:

```json
{ "error": { "code": "validation_error", "message": "One or more fields are invalid",
             "details": [{ "field": "right_eye_axis", "message": "..." }] } }
```

| Area | Endpoints |
|---|---|
| Auth | `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout`, `GET/PUT /auth/me`, `POST /auth/change-password` |
| Users | `GET/POST /users`, `GET/PUT /users/{id}`, `POST /users/{id}/reset-password`, `GET /users/doctors` |
| Patients | `GET/POST /patients`, `GET /patients/search?q=`, `POST /patients/check-duplicates`, `GET /patients/by-code/{code}`, `GET/PUT/DELETE /patients/{id}`, `POST /patients/{id}/restore`, `GET /patients/{id}/checkups`, `GET /patients/{id}/followups` |
| Check-ups | `GET/POST /checkups`, `GET/PUT /checkups/{id}`, `GET /checkups/{id}/pdf` |
| Follow-ups | `GET/POST /followups`, `GET /followups/pending`, `GET /followups/counts`, `GET/PUT /followups/{id}` |
| Reports | `GET /reports/dashboard`, `GET /reports/generate?report_type=`, `GET /reports/patients`, `/reports/checkups`, `/reports/followups`, `GET /reports/export/{pdf,excel,csv}?report_type=` |
| Audit | `GET /audit-logs`, `GET /audit-logs/facets` |
| Health | `GET /health`, `GET /config` |

List endpoints return `{items, total, page, page_size, pages}` (maximum `page_size` is 100).

**Authentication flow.** Login returns a 30-minute access token in the body; the frontend keeps it in memory only. A 7-day refresh token is set as an `httpOnly`, `SameSite=Strict` cookie scoped to `/api/auth`. Refresh rotates the token. Reusing a rotated token more than 10 seconds later is treated as theft and revokes all of that user's sessions (the 10-second window covers two tabs refreshing at once). Five failed logins lock the account for 15 minutes.

## Testing

### Backend (pytest)

```powershell
cd backend
.venv\Scripts\activate
pytest
```

Tests run only against `TEST_DATABASE_URL`, and refuse to start unless that database name contains `test`. The suite rebuilds the schema with the real Alembic migrations, then truncates all tables between tests. It covers authentication and token rotation, role-based authorization, registration, duplicate detection, search (including wildcard and SQL-injection input), updates and soft delete, check-up creation/retrieval/history/idempotency, measurement validation, follow-up management, report calculations, PDF/Excel/CSV generation, audit log immutability, and unauthorized requests.

### Frontend (Vitest + React Testing Library)

```powershell
cd frontend
npm test
```

Covers formatting and age utilities, the permission map, API error handling, patient form validation, live duplicate warnings, eye-measurement validation, dialogs, pagination and route protection.

### Browser end-to-end workflow (Playwright)

With the backend (`:8000`) and frontend dev server (`:5173`) running against a seeded **development** database:

```powershell
backend\.venv\Scripts\pip install -r e2e\requirements.txt
backend\.venv\Scripts\python e2e\workflow_e2e.py           # uses installed Microsoft Edge
# or: python -m playwright install chromium; set E2E_BROWSER=chromium
```

It walks the full workflow: the receptionist logs in and registers a patient, and the patient appears in the list. The doctor finds the patient by mobile number, adds a check-up with follow-up, and downloads its PDF. The admin opens the examination report, downloads PDF and Excel, and checks the audit log. It finishes with a mobile-layout check and saves screenshots to `e2e/screenshots/`. Each run adds one synthetic patient and check-up.

## Security and privacy

- Passwords hashed with bcrypt (cost 12); strength rules on creation and change; login lockout; constant-time handling of unknown usernames.
- Short-lived JWT access tokens kept in memory; rotating httpOnly refresh cookie with reuse detection; logout and password change revoke sessions.
- RBAC on every endpoint. Reception staff cannot read clinical data. Doctors can only edit their own examinations.
- All queries go through the SQLAlchemy ORM with bound parameters, and `LIKE` wildcards in search input are escaped.
- Pydantic validates every request and the database enforces CHECK, FK and UNIQUE constraints.
- CORS is restricted to configured origins. Security headers are set (nosniff, frame deny, no-referrer, `no-store` on API responses), and nginx adds a Content Security Policy.
- The audit log records logins, failed logins, patient and check-up views, create/update/deactivate actions with before/after values, and exports. It is append-only at the database level and never stores password hashes.
- Patients are soft-deleted; clinical history is preserved.
- Secrets come from the environment. `.env` files are git-ignored, and `alembic.ini` contains no credentials.
- Exported spreadsheets neutralise formula injection.

**Before going live:** serve over HTTPS with `COOKIE_SECURE=true`, use strong unique secrets, restrict network access to the database, set up the backups described in [docs/BACKUP_AND_RECOVERY.md](docs/BACKUP_AND_RECOVERY.md), and review data-retention and consent requirements with the hospital's data protection officer. In India, that includes the Digital Personal Data Protection Act 2023 and any state health department rules.
